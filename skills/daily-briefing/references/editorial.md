# Editorial rules

Score each dimension 0–5. Overall score: impact 25%, novelty 15%, evidence 20%, technical SE relevance 20%, customer-facing SE relevance 20%. Explain the score in one sentence. A score of 3.5 is a starting threshold, not a quota; a major verified launch may be included with a clear reason.

Technical SE relevance includes architecture, integrations, latency/cost tradeoffs, evaluation, security constraints, deployment, and reproducible demos. Customer-facing relevance includes discovery questions, enterprise readiness, use cases, adoption barriers, and evidence-backed competitive comparisons. Avoid recommending a vendor from marketing claims alone.

Plain English edition: aim for a five-minute read. Per event: what happened, why it matters, a customer talking point. Explain unfamiliar concepts in ordinary words. Avoid unexplained acronyms.

Technical edition: aim for eight to ten minutes. Per event: concrete change, implementation implications, availability and constraints, something to test or a useful question. Distinguish announced, preview/waitlist, and generally available. Never invent benchmarks, prices, licensing, API fields, or release dates.

Both editions cite sources. Use concise original summaries, not copied article paragraphs. Source dates and event dates may differ. Label older context; do not pass it off as a new development. Mention important coverage gaps in a short footer. If no worthwhile verified news is found, produce a short quiet-day edition only if collection worked; if collection broadly failed, report failure instead.

Optional “Worth trying” and “Coming up” items need verified URLs and, for events, actual dates/timezones. Include only when useful. Do not fill empty sections.
